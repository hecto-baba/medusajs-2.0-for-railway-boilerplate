# Appointment Booking — Plan 3: Multi-Resource, Calendly-Style Booking (Seller First)

Supersedes the open items in `APPOINTMENT_BOOKING_MODULE_PLAN.md` and `..._PLAN2.md`. Those plans built the foundation; this one finishes the product.

## 1. The goal

A business signs up, logs in, onboards, and sets up its store. After approval it can:

- create **many resources** (a stylist, a doctor, a room, a trainer),
- give **each resource** its own weekly hours, holidays, session length, capacity per slot, buffer time, and booking rules,
- price the services, with pricing rules,
- see and manage appointments.

A **buyer** browses businesses, picks a service and a resource, sees real open slots in their own timezone, pays, and gets a confirmation. Two buyers can never take the same slot.

Priority order: **seller first**, then buyer, then admin oversight.

## 2. Decision: build on our module, not the RSC Labs plugin

Audited line by line (see the audit notes in the conversation / section 12). The plugin is a day-rental engine: no weekly hours, no session slots, no capacity, no buffer, no timezone, no business ownership, no overlap check on any write path, booking rules stored but never enforced, abandoned holds never expire. Making it meet this goal means rewriting most of it. Our `appointment-booking` module already has the hard parts that cannot be bolted on later:

- weekly recurring hours and holiday exceptions,
- a **database exclusion constraint** against overlapping bookings (`appointment_no_overlap`),
- a **database trigger** against exceeding slot capacity (`appointment_attendee_capacity_check`),
- links to products, orders and vendor admins.

The plugin stays installed and **untouched and unused** (as Plan 1 decided). Its pre-existing public store routes have no customer auth; Task 1.6 locks them down so they are not an open attack surface while installed.

**Ideas borrowed from the plugin:** layered rules with priority and validity windows, a cart hold with expiry, and the admin screen layout.

## 4. Design decisions (made here so the build is not blocked)

1. **Resource = the existing `provider` table, extended.** Keep the table, the constraint and the trigger exactly as they are (zero risk to the guards). Add `vendor_id`; drop the unique on `vendor_admin_id`. The UI and new API call it **Resource**. Code keeps the `Provider` model name to avoid a risky rename migration.
2. **Offerings = the existing `service_provider` join** (resource ↔ Medusa product). A seller's service is a normal Medusa product they already own; its variant price is the base price. Adds optional per-offering duration and capacity overrides.
3. **Slots are computed live; a booking row is created only when someone reserves.**
   - No "generate slots" chore, no stale or orphan rows.
   - A slot is bookable if no existing booking blocks it, or an existing booking with the **identical** start/end has spare capacity (group sessions).
   - The first reservation creates the `appointment` row under a lock; later reservations join it. The DB guards still backstop everything.
4. **Buffer is enforced in the database too:** `appointment` gets `block_start` / `block_end` (start minus buffer-before, end plus buffer-after) and the exclusion constraint is rebuilt on those. Two bookings can never overlap including their buffers, even through a bug.
5. **Reserve before pay, not after.** Add-to-cart creates a **hold** (attendee `reserved`, with `expires_at`). Completing the cart confirms it. A job that runs **every minute** releases expired holds. This removes the "paid but no booking" failure.
6. **The server computes the price. The client never sends one.** Base = the variant's calculated price in the cart's currency/region; then pricing rules apply; the result is set as the line item's `unit_price`.
7. **Guests can book.** The attendee stores `buyer_name`, `buyer_email`, `buyer_phone?`, `notes?`; `customer_id` becomes optional.
8. **Timezone:** each resource has an IANA timezone. Weekly hours are local to it. The buyer sees slots in their own timezone (with a switcher). Stored times are UTC. Use `luxon` for DST-safe conversion (add the dependency if absent; check `package.json` first).
9. **Booking rules live on the resource** (with a "copy to all my resources" action). MVP set: `session_duration_minutes`, `slot_step_minutes`, `capacity`, `buffer_before_minutes`, `buffer_after_minutes`, `min_notice_minutes`, `max_advance_days`, `hold_minutes`, `cancellation_window_hours`.
10. **Pricing rules (MVP):** per vendor, optionally scoped to a resource and/or product. Types: `percent_adjust`, `fixed_adjust`, `override_price`. Conditions: weekday set and/or local time band, validity dates. Highest priority wins; ties broken by most specific scope.
11. **Cancellation never refunds automatically** (unchanged confirmed decision). It frees the slot and records who cancelled and why.
12. **Admin is oversight.** Admin routes are thin wrappers over the same service layer, with no ownership check, and come last.

13. **"Block this slot"** needs no new model: it creates a partial-day blackout exception for that slot's time window (Phase 4.5 / 5.4). It appears in the Preview tab per slot.

### Defaults taken for open questions (change these before Phase 2 if you disagree)

| Question | Default in this plan |
|---|---|
| Services per resource | **Several**, each with optional duration/capacity override (offerings, 2B) |
| Buyer flow | Business → resource → service → time. "Any available resource" is out of scope. |
| Stored vs computed slots | **Computed live**, saved only when booked (decision 3). The seller sees the full generated list in Preview. |
| Pricing rules UI | Weekday / time-band price changes, as in screen S8 |

### Worked example of slot generation (the contract the engine must satisfy)

Settings: session 15 min, capacity 2, hours 09:00–13:00 and 14:00–17:00, no buffer.

- Morning = 16 slots, afternoon = 12 slots → **28 slots/day, 56 seats**.
- First booking on 09:15–09:30 shows `1/2`; second shows `2/2` (full, hidden from buyers); a cancellation reopens it.
- With a 15-minute buffer after, a booking at 09:15–09:30 blocks 09:15–09:45, so the 09:30 slot is not offered (unless it is the same window with spare capacity).
- A 45-minute session with slot step 30 offers starts at 09:00, 09:30, 10:00…; a booking blocks every overlapping start.

### Out of scope for this plan (later)

Approval-first booking, multi-day/recurring bookings, intake questions, reminders, calendar sync (Google/ICS), reschedule, automatic refunds, "any available resource" round-robin, deposits, tiered/package pricing.

## Phase 3 — Availability engine v2 (the core)

One pure, testable module: `src/modules/appointment-booking/lib/availability.ts`, used by the service. Replaces `expandAvailableSlots`.

Inputs: a resource (with settings), an offering (duration/capacity overrides), a date range, `now`, the resource's recurring rules and exceptions, and its existing non-cancelled appointments (with active attendee counts).

- [ ] 3.1 **Timezone:** convert each local weekly window (`day_of_week` + "HH:mm", evaluated in the resource's timezone) to UTC per calendar day with luxon (DST-safe). Day-of-week is the **local** weekday.
- [ ] 3.2 **Exceptions:** whole-day blackout (null times) removes the day; **partial blackout** (start and end) subtracts a window; `extra_hours` adds a window. Fix the current bugs: a blackout with only one of start/end is rejected by validation (Task 3.9); load exceptions for the whole local day even when `date_from` is mid-day.
- [ ] 3.3 **Candidate slots:** step through each window by `slot_step_minutes` (default = duration); a candidate fits if `start + duration <= window.end`.
- [ ] 3.4 **Buffers:** a candidate's block is `[start - buffer_before, end + buffer_after)`. It is bookable if its block overlaps no existing appointment block, **or** an existing appointment has the identical start/end and spare capacity.
- [ ] 3.5 **Notice and horizon:** drop slots earlier than `now + min_notice_minutes` or later than `now + max_advance_days`.
- [ ] 3.6 **Output per slot:** `{ start, end, capacity_remaining, appointment_id? }` (id only if a booking row already exists).
- [ ] 3.7 **Range guard:** reject ranges over 62 days and cap results, to stop cheap denial-of-service reads.
- [ ] 3.8 `isSlotBookable(resource, offering, start, now)`: recompute for that single slot and return the decision. **Every reservation re-validates through this**, so a buyer can never book a time that is not genuinely offered (outside hours, inside a blackout, past, too far ahead, off-grid).
- [ ] 3.9 Validation in the create-exception / create-recurring workflow steps: `HH:mm` format, `start < end`, partial blackout requires both times, `effective_until >= effective_from`, and reject overlapping weekly windows for the same resource and day.
- [ ] 3.10 **Automated tests** (this plan adds tests for this module only, because it is pure logic and the heart of the product): a New York 09:00–17:00 rule yields 14:00–22:00 UTC in winter and 13:00–21:00 UTC in summer; the DST-change day; a blackout day; a partial blackout; extra hours; buffer exclusion; min-notice and max-advance cut-offs; group capacity remaining; an identical-window booking with spare capacity stays bookable; an overlapping different-length booking does not.

### Completion checklist

- [ ] A new business signs up, onboards, gets approved, and only then can use appointments (the server enforces this).
- [ ] The business creates two resources with different timezones, hours, session lengths, capacities and buffers; slots differ accordingly.
- [ ] A holiday removes that day's slots; a partial blackout removes only that window.
- [ ] Minimum notice and maximum advance hide the right slots.
- [ ] Pricing rules change the displayed and charged price; the client cannot influence it.
- [ ] A buyer (guest and logged-in) books, pays by Stripe, gets an order and an email.
- [ ] Two buyers racing for the last spot: exactly one wins; the database refuses the other even with the app lock bypassed.
- [ ] A group slot (capacity 3) accepts three bookings and rejects the fourth.
- [ ] Buffer time is honoured, in the UI and in the database.
- [ ] Abandoned holds free themselves.
- [ ] Vendor and buyer cancellation free the slot and trigger **no** refund.
- [ ] Vendor A cannot read or change vendor B's resources, rules or bookings.
- [ ] Timezone and DST cases are correct (covered by the Phase 3 tests).

## Suggested build order and sizing

1. Phase 0–1 (hotfixes) — about 1–2 days. Ship first.
2. Phase 2–3 (model + engine + tests) — about 4–5 days. Highest-risk, highest-value; do not rush.
3. Phase 4–5 (seller API + UI) — about 6–8 days. This delivers the seller-first milestone: a business can fully self-manage and preview.
4. Phase 6 (booking flow) — about 5–6 days, including the price spike.
5. Phase 7 (buyer) — about 5–6 days.
6. Phase 8 (admin) — about 3–4 days.
7. Phase 9 — about 2 days.

**Milestone A** (after Phase 5): a seller can run a complete calendar and preview what buyers will see.
**Milestone B** (after Phase 7): end-to-end signup → booking works.
**Milestone C** (after Phase 9): admin oversight and hardening done.

## Risks and how this plan handles them

| Risk | Handling |
|---|---|
| Migration touches the double-booking constraint | Done as one hand-written, reversible migration, tested with a scratch overlap script before anything else is built on it (Phase 2 verify). |
| `unit_price` and tax/region pricing mismatch at checkout | Dedicated spike at the start of Task 6.3 before building on it. |
| Only one handler can own `completeCartWorkflow` hooks (rentals already do) | Phase 6 changes only the existing `complete-cart-marketplace` composition, never adds a second hook. |
| DST and timezone mistakes | luxon + the Phase 3 test suite, run before any UI is built. |

| Old data from the pre-generation approach | Phase 2 cleanup deletes only empty `available` rows; booked history is untouched. |
