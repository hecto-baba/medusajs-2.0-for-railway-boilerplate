# Learning Log — medusajs-2.0-for-railway-boilerplate

## Vendor Collection Authorization & Search Input Focus Retention — 2026-09-24

**What was used:** Multi-tiered vendor session token resolution (`req.cookies`, `Authorization` header, raw `Cookie` header fallback in Next.js proxy route), explicit route-level `authenticate("vendor", ["session", "bearer"])` in backend middlewares with pre-resolved `vendor_id` fallback in `POST /vendors/collections`, and TanStack Query `placeholderData: keepPreviousData` coupled with page reset on search in `@medusajs/ui`'s `useDataTable`.
**Why this over alternatives:** In Next.js 15 App Router Route Handlers, `await cookies()` from `next/headers` can resolve empty or lose context on client-side `fetch` POST mutations, leading to a false 401 Unauthorized before reaching the backend; accepting `req.cookies` guarantees immediate token presence. In `@medusajs/ui`'s `DataTable.Search`, without `keepPreviousData`, any keystroke invalidating the query key clears `data` to `undefined`, making `rows.length === 0` and `isLoading === true`, which trips `showSkeleton` and replaces the `<Input>` with `<DataTableSearchSkeleton>`, unmounting the DOM node and dropping user input focus.
**Alternatives considered:** Using `setTimeout` or debounced state without `keepPreviousData`; rejected because even with debounce, whenever the query key updates, `data` is dropped if not retained by `keepPreviousData`, causing the skeleton flash and loss of active DOM focus.
**Core concept to remember:** In `@medusajs/ui`'s `useDataTable`, `showSkeleton = isLoading && rows.length === 0`. In React Query v5, updating a query key sets `data = undefined` while fetching unless `placeholderData: keepPreviousData` is supplied. When `showSkeleton` flips to true, `DataTable.Search` unmounts `<Input>` and renders `<Skeleton>`, dropping focus. In Next.js 15 Route Handlers, always extract cookies directly from `NextRequest.cookies` or request headers rather than relying solely on `next/headers`'s `cookies()`.

## Products Options & Collections Filter/Sort Parity with Backend Production — 2026-09-24

**What was used:** Extended vendor Product Options and Collections endpoints with date filtering (`created_at`, `updated_at`, `created_at_gte`, `updated_at_gte`) and exclusivity filtering (`is_exclusive`); configured `@medusajs/ui` `useDataTable` with `filterHelper.accessor("is_exclusive", { type: "radio", label: "Type", options: [{ label: "Product-specific", value: "true" }, { label: "Global", value: "false" }] })` and date range options; rendered `<DataTable.FilterMenu>` and `<DataTable.SortingMenu>` in both tables; added hidden-by-default `updated_at` sortable column with explicit `sortAscLabel: "Ascending"` and `sortDescLabel: "Descending"` directions to fulfill all sorting criteria without cluttering table layout.
**Why this over alternatives:** In Medusa Admin, Product Options are classified as either Product-specific or Global via the `is_exclusive` boolean flag, and Collections support sorting by `Title`, `Handle`, `Created`, and `Updated`. Sellers need identical visibility to filter and organize both options and collections according to the exact same criteria as backend production admins.
**Alternatives considered:** Using simple text filters or omitting the date range comparisons; rejected because Medusa's standard table filters use presets (Today, Last 7/30/90 days) and date comparison operators (`$gte`, `$lte`), which are natively rendered by `@medusajs/ui`'s date filter component.
**Core concept to remember:** In Medusa 2.0, product options with `is_exclusive: true` are scoped specifically to a single product, whereas `is_exclusive: false` designates shared or global options. In `@medusajs/ui`, table sort menus discover all columns with `enableSorting: true`; using `columnVisibility: { state: { updated_at: false } }` keeps secondary timestamp columns sortable from the Toolbar menu without consuming valuable horizontal table real estate.

## Inventory Dimensions Units & Full Filter/Sort Parity with Backend Production — 2026-09-24

**What was used:** Standardized metric dimension units (`Height (cm)`, `Width (cm)`, `Length (cm)`, `Weight (g)`) across inventory forms, drawers, and detail views; expanded vendor inventory items backend schema and endpoint to support all 9 Medusa Admin filters (`location_id`, `material`, `sku`, `mid_code`, `height`, `width`, `length`, `weight`, `requires_shipping`); aligned sort options (`Title`, `SKU`, `In Stock`, `Reserved`) with explicit `sortAscLabel: "Ascending"` and `sortDescLabel: "Descending"`, backed by in-memory sort fallbacks for computed multi-location quantities.
**Why this over alternatives:** Without explicit units, sellers risk entering dimensions in arbitrary units (e.g. inches or kilograms) which causes fulfillment rate miscalculations. For the inventory list, full filter and sort parity with Backend Production gives sellers identical capabilities to manage their inventory levels across multiple stock locations without missing any attribute filters or sort options.
**Alternatives considered:** Leaving unit labels implied or generic; rejected because Medusa fulfillment and carrier integrations strictly assume centimeters and grams. For sorting, attempting database-level SQL sort on computed sums (`stocked_quantity` across `location_levels`) can fail or become overly complex in MikroORM graph queries; sorting in-memory on the computed inventory array ensures safety and accuracy.
**Core concept to remember:** In Medusa, inventory dimension attributes always adhere to the metric standard (`cm` for length/width/height, `g` for weight). In multi-location inventory architectures, `stocked_quantity` and `reserved_quantity` are aggregated dynamically from child `inventory_levels` rather than static database columns on `inventory_item`; when supporting table sorting by these virtual metrics, compute the aggregations before applying the sort order.


## Vendor Onboarding Gatekeeper & Admin Approval State Machine — 2026-09-17

**What was used:** Persistent multi-stage onboarding store (`onboardingStore`) on Medusa backend combined with client-side route gatekeeping in `PanelShell` and `Sidebar`.
**Why this over alternatives:** Strictly gating non-approved vendors at the shell level ensures no sensitive commercial tools (catalog, orders, inventory, pricing) are exposed before compliance review, while centralizing approval/rejection state transitions in Medusa prevents silent auto-approvals.
**Alternatives considered:** Permissive open access with warning banners only; rejected because vendors must complete verification before gaining marketplace merchant privileges.
**Core concept to remember:** Vendor lifecycle must follow a strict state machine: `DRAFT` → `UNDER_REVIEW` → (`APPROVED` | `REJECTED`). Newly registered vendors are kept strictly on `/onboarding` until an admin explicitly audits and approves the application from `/admin/vendor-applications`.

## Vendor 360° Admin Integration (Medusa 2.0 Query Graph & Tabbed UI) — 2026-09-14

**What was used:** Medusa 2.0 `query.graph` multi-entity scoping on backend, combined with `@medusajs/ui` Tabs & DataTable components in admin UI.
**Why this over alternatives:** Querying the graph allows deep cross-module relational querying (products, collections, categories, inventory, orders, customer links, price lists, promotions, venues, shows) in a single structured response, while `@medusajs/ui` Tabs provide native design consistency matching Medusa Admin standards.
**Alternatives considered:** Fetching data via 8 separate client-side API requests; rejected because it creates multiple round trips and loading waterfalls instead of instant tab navigation.
**Core concept to remember:** Medusa 2.0 uses Remote Links to bind custom module data (like Marketplace vendors) to core commerce modules (Products, Inventory, Orders). `query.graph` resolves across these link boundaries seamlessly in unified DML queries.

## Inventory & Reservations 100% Medusa Admin Alignment — 2026-09-15

**What was used:** Medusa UI `<Container className="divide-y p-0">`, `useDataTable`, `ActionMenu`, `SectionRow`, and Two-Column detail layouts matching `@medusajs/dashboard` 1:1.
**Why this over alternatives:** Strictly conforming to the official `@medusajs/dashboard` layout, text copy, column definitions, and confirmation dialogs ensures the Seller Panel behaves identically to Medusa Admin, eliminating cognitive load and UI inconsistencies for vendors and admins.
**Alternatives considered:** Custom dashboard cards and custom modal layouts; rejected in favor of Medusa Admin standard drawers, attribute grids, and table actions.
**Core concept to remember:** In Medusa 2.0, Inventory Items are distinct from Product Variants and are linked to Stock Locations via Inventory Levels (`inventory_levels`). Reservations allocate a specific portion of the stocked quantity at a location, leaving `available = stocked - reserved`. All UI copy and operations strictly reflect this exact tripartite model (`stocked`, `reserved`, `available`).
## TrustClaw Master Catalog JSON Attributes Tabular Presentation — 2026-09-19

**What was used:** Dynamic attribute extraction utility (`extractProductAttributes`), title-case formatting with acronym preservation (`formatAttributeKey`), and an interactive tabular component (`TrustClawAttributesSection`) with client-side search, value type badge detection, text truncation, JSON copy, and metadata sync editing drawer.
**Why this over alternatives:** Rather than leaving rich imported specifications as an unreadable stringified JSON dump in the Metadata card or hiding them from the shipping-only Medusa Attributes section, a dedicated specifications table directly below Attributes provides clean readability, searchability, and vendor editability while staying visually cohesive with `@medusajs/ui`.
**Alternatives considered:** Flattening all JSON attributes into separate top-level metadata keys; rejected because it pollutes root product metadata and would conflict with standard metadata keys. Another alternative was a read-only code block; rejected because vendors need clean tabular key-value readability and the ability to edit specifications.
**Core concept to remember:** When importing catalog data from external syndication sources (like TrustClaw Master Catalog) into Medusa 2.0, store specifications under a structured `metadata.attributes` namespace and provide a dual-mode presentation: a clean tabular UI for day-to-day viewing/filtering and an inline drawer to modify the underlying JSON safely via `updateVendorMetadata`.

## Seller Panel Promotions & Price List Products Filter and Sort Parity — 2026-09-24

**What was used:** Full filter and sorting schema parity between Medusa Admin and Seller Panel using `@medusajs/ui` DataTable helper utilities (`createDataTableFilterHelper`, `columnHelper`), supporting `type_id`, `tag_id`, `sales_channel_id`, `status`, `created_at_gte`, and `updated_at_gte`, paired with backend schema validation and `query.graph` filtering/ordering in vendor endpoints.
**Why this over alternatives:** Rather than letting the Seller Panel diverge in available filter options (missing tags, sales channels, types, or updated timestamps) and sort directions from Medusa Admin Backend Production, strictly aligning the filters and columns ensures identical behavior, predictable searchability, and uniform UX across both panels.
**Alternatives considered:** Keeping hardcoded client-side filtering or relying only on creation date; rejected because vendor catalogs scale and require filtering by tags, channels, types, and modification timestamps (`updated_at`), matching the Medusa Admin experience.
**Core concept to remember:** In `@medusajs/ui`'s `useDataTable`, `DataTable.FilterMenu` options are governed by the `filters` array passed to the hook, and `DataTable.SortingMenu` derives its options from columns with `enableSorting: true`. To match Medusa Admin's ascending/descending UI, specify `sortAscLabel: "Ascending"` and `sortDescLabel: "Descending"` on sortable column definitions.

## Customer Filter & Sort Parity and Stock Location Availability Fallback — 2026-09-24

**What was used:** Extended vendor customer backend filtering (`groups` and `updated_at_gte`) and TanStack Table column visibility (`first_name`, `last_name`, `updated_at`) with explicit sorting labels (`sortAscLabel: "Ascending"`, `sortDescLabel: "Descending"`), coupled with `listVendorStockLocations` dedicated API query in `InventoryCreateForm` Availability section.
**Why this over alternatives:** Aligning Customers filters (`Customer Groups`, `Account Created`, `Updated`, `Account`) and sort options (`Email`, `First Name`, `Last Name`, `Account Created`, `Updated`) with Medusa Admin Backend Production provides complete feature parity for sellers without visual clutter. For inventory creation, querying `listVendorStockLocations` (with fallback to default store locations and address resolution) guarantees that sellers always see available stock locations and "In Stock" quantity inputs rather than a false "No stock locations available" state.
**Alternatives considered:** Relying solely on `taxonomy` without address resolution; rejected because `stock_locations` requires dedicated address enrichment and fallback logic when vendor-specific links haven't been created yet.
**Core concept to remember:** In `@medusajs/ui`'s `useDataTable`, `DataTableSortingMenu` exposes all sortable columns registered in `instance.getAllColumns()`. Defining accessor columns with `enableSorting: true` while hiding them from visible table rendering via `columnVisibility: { first_name: false, last_name: false, updated_at: false }` allows sorting by fields (like individual First/Last Name) that are grouped together in composite cells (like Full Name) without corrupting the table layout.
